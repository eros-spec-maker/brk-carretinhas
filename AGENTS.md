"# AGENTS.md \u2014 Padr\u00e3o de Trabalho (obrigat\u00f3rio para QUALQUER agente, qualquer modelo)\n\nEste documento define o processo padr\u00e3o do projeto **BRK Carretinhas** (loja de carretinhas de carga \u2014 app Base44: https://brk-haul-pro.base44.app).\n\n## 1. Gest\u00e3o de tarefas \u2014 GitHub Issues\n- Toda tarefa (Corre\u00e7\u00e3o, Melhoria ou Nova fun\u00e7\u00e3o) DEVE ser criada como **Issue** neste reposit\u00f3rio ANTES do trabalho come\u00e7ar.\n- Labels obrigat\u00f3rias (uma por Issue): `corre\u00e7\u00e3o` (bug/regress\u00e3o), `melhoria` (refatora\u00e7\u00e3o, UX, perf), `nova-fun\u00e7\u00e3o` (funcionalidade nova), `seguran\u00e7a` (hardening, quando aplic\u00e1vel).\n- A Issue deve conter: contexto, resultado esperado e crit\u00e9rios de aceita\u00e7\u00e3o.\n\n## 2. Deploys via Pull Requests\n- Todo trabalho entra via **Pull Request**. A descri\u00e7\u00e3o do PR DEVE mencionar a Issue com `Closes #N`.\n- Merge do PR = deploy. Nenhum deploy fora do fluxo de PR.\n- PRs pequenos e focados; um PR n\u00e3o mistura corre\u00e7\u00e3o com melhoria.\n\n## 3. Padr\u00f5es de seguran\u00e7a (inegoci\u00e1veis)\n1. **Segredos:** chaves de API NUNCA no front-end, c\u00f3digo, bundle ou Git. Sempre vari\u00e1veis de ambiente. Permiss\u00f5es de chave no m\u00ednimo necess\u00e1rio.\n2. **Arquitetura:** front-end n\u00e3o acessa o banco diretamente; tudo passa pela API/back-end com valida\u00e7\u00e3o server-side. Princ\u00edpio do menor privil\u00e9gio.\n3. **Dados:** exibir apenas o necess\u00e1rio; senhas nunca expostas; dados sens\u00edveis criptografados; sem exposi\u00e7\u00e3o de dados de outros usu\u00e1rios (RLS ativo).\n4. **Entradas:** validar e sanitizar no front-end E back-end; limitar tamanho/formato; prote\u00e7\u00e3o contra SQL Injection e XSS (escaping contextual + CSP quando aplic\u00e1vel).\n5. **Auth:** autentica\u00e7\u00e3o e autoriza\u00e7\u00e3o SEMPRE no back-end; verifica\u00e7\u00e3o de permiss\u00e3o a cada requisi\u00e7\u00e3o; senhas com hash seguro (bcrypt/Argon2); esconder bot\u00e3o/rota no front N\u00c3O \u00e9 controle de acesso.\n6. **Monitoramento:** registrar eventos importantes (login falho, bloqueios, atividade suspeita); sem dados sens\u00edveis em logs; alertas para comportamento anormal.\n7. **Abusos:** rate limiting nas APIs; limitar tentativas de login consecutivas; bloqueio/atraso progressivo; CAPTCHA quando necess\u00e1rio; endpoints cr\u00edticos protegidos contra ataques automatizados.\n8. **Erros:** respostas de erro sem stack traces, secrets ou informa\u00e7\u00f5es internas.\n9. **Auditoria:** testar acesso horizontal/vertical indevido (IDOR/BOLA) antes do deploy; rodar testes de regress\u00e3o antes do merge; nenhuma corre\u00e7\u00e3o de seguran\u00e7a pode quebrar funcionalidades.\n\n## 4. UX/Motion (princ\u00edpios de motion \u2014 todo elemento)\n- Skeleton loaders em toda \u00e1rea que carrega dados.\n- Lazy loading de imagens com transi\u00e7\u00e3o suave.\n- Anima\u00e7\u00f5es de entrada/sa\u00edda suaves (fade + translate 8-12px, 200-300ms ease-out) em cards, modais, se\u00e7\u00f5es e filtros.\n- Estado de progresso vis\u00edvel em toda a\u00e7\u00e3o (spinner + disabled durante envios).\n\n## 5. Regra de auditoria de secrets\nSe encontrar um secret real exposto: NUNCA copiar o valor para relat\u00f3rios/Issues/PRs. Identificar a vari\u00e1vel, remover a exposi\u00e7\u00e3o e recomendar/executar a rota\u00e7\u00e3o.\n"
